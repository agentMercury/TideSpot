## 3. 优化需求池（生效时点：v1 交付验收签署之后）

**优先级定义**
- **P1** 完工后首个迭代就做：影响数据可信度、安全、或后续迭代成本，越晚改代价越高
- **P2** 有价值、可排入 1～2 个迭代
- **P3** 探索性 / 依赖外部条件 / 锦上添花

## 4. 三个我最想推的想法（展开）

### 4.1 FO-01 安全闸门：先回答「能不能去」，再回答「好不好钓」

现在的 0–100 分把「鱼情」和「人身安全」揉进了一个数。雷暴硬否决 ×0.05 之后，一个 6 分的小时可能仍被渲染成「别去」的红色，但大风 45 km/h、浪高 1.7 m 这类连续衰减会让分数落到 50 左右——用户看到的是「可以」，实际是「站不稳」。建议把 `VetoEvaluator` 的输出从「中文原因列表」升级为**结构化安全事件**（code / 严重度 / 触发值 / 阈值），UI 在 5 Tab 之上放一条独立安全条：

```
[红] 不建议出钓 · 阵风 52 km/h（阈值 45）· 浪高 1.8 m（阈值 1.6）
     钓鱼指数 47 分「较差」 ← 分数只描述鱼情，不再承担安全表达
```

顺带解决 `BestWindowFinder.kt:118` 用 `contains("雷暴")` 判雷暴的问题——英文文案下这会漏掉安全否决，属于「i18n 引发安全缺陷」，优先级应高于普通多语言打磨。

### 4.2 FO-02 点位置信度：把「估算」两个字讲清楚

SRS 已经诚实承认「中国境内多数点位水质为模型估算值」，但一个「估算」徽标承载不了用户对「我该不该按这个数出门」的判断。建议把置信度做成**可下钻的四分量**，并让每个分量指向一个用户可执行的改善动作：

| 分量 | 数据来源 | 低分时用户能做什么 |
|---|---|---|
| 数据源覆盖 | 5 维各有哪些是实测/卫星/模型/估算 | 手动录入一次实测水温（§6.1.3） |
| 网格距离 | 选点到最近有效模型格点 | 换到相邻更靠近水域的点 |
| 数据陈旧 | TTL + 本机拉取时刻 | 下拉刷新（需 FO-17 修好 force） |
| 校正状态 | `calibration` 表 r / 样本数 | 再记 1 条涨潮时刻即可校潮（§6.2b 规则 5） |

这个设计把分散在 §6.2b、§6.7、§8.2、§9.6 的零散机制串成一条用户能理解的叙事，也是 FO-03 个人化校正的天然入口。

### 4.3 FO-03 预报回放：让经验模型自己变准

SRS §3 禁止账号/云同步/社交，但不禁止**本机**积累历史。当前每次刷新覆盖旧数据，等于把最有价值的资产（「当时预报了什么」）丢掉了。建议：

1. 每次成功刷新保留一份轻量快照（小时 epoch + 分数 + 关键因子 + `algoVersion`），按点滚动保留 90 天，压缩后占用可控；
2. 用户出钓回来做一次 1–5 星体感打分（可选、可跳过、可全删）；
3. 本地按「点 × 场景预设」统计「预报分 vs 体感」的残差，产出很小的偏置修正（设上限，例如 ±5 分），默认关闭；
4. 设置页可看「这个点你的反馈让指数平均下调了 3 分」，并可一键清除全部反馈。

**收益**：不需要服务端、不违反 §3、不引入红线源，却让一个静态经验加权模型具备长期改进能力；同时为 FO-10 的算法实验提供真实数据依据。**风险**：反馈样本稀疏时容易过拟合，必须设最小样本数、修正上限和默认关闭，并在 UI 明示「个人偏置仅供参考」。
