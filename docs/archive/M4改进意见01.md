## 1. 总体结论

**建议 M4 判定由「✅ 通过 / F-3.1~F-3.8 全过」调整为「有条件通过」。**

理由：数据层与算法层的 M4 附加必修 1–8 确实扎实落地，377 个单测可独立复现且全绿，这是真实成绩；但 **UI 层存在「组件写完了、接线没做完」的系统性落差**——Tab 标题数组错位、数值表同向嵌套滚动容器、评分双管线口径分裂、档位文字/置信徽标组件从未被生产代码调用。这些都不是风格问题，而是会让用户在真机上看到错误标题、切换数值表即崩溃、同一收藏点在详情页与 Top10 显示两套分数的问题。台账「F-3.1~F-3.8 全过」与 CHG-12 自己登记的 ④(a)(b) 接线缺口也自相矛盾。

### 2.3 图表 y 轴算法的数值复现（不改代码，按 `ChartMath.yAxis` 逐行等价复算）

| 输入序列 | `niceStep` 结果 | 实际 y 轴 | 归一化高度 |
|---|---|---|---|
| 浪高 `0.20~0.40 m` | 1.0 | `[0.0, 1.0]`，刻度仅 0/1 | 0.20 / 0.28 / 0.35 / 0.40 |
| 潮位 `0.10~0.30 m` | 1.0 | `[0.0, 1.0]`，刻度仅 0/1 | 0.10 / 0.17 / 0.24 / 0.30 |
| 低分区指数 `20~40 分` | 2.5 | `[17.5, 42.5]` | 0.10 / 0.42 / 0.62 / 0.90 |

根因：`niceStep` 的 `base` 从 `1.0` 起只乘 10，缺 10 的负幂，任何 `span < 1` 的量纲（浪高、潮位、浊度、叶绿素）步长恒为 1.0，曲线被压进绘图区底部 10%–40%；BAR 模式又共用自适应轴，柱底不是 0，20 分与 40 分被画成 10% 与 90% 高，视觉夸大近 2 倍。`ChartMathTest` 的 `yAxisAdaptsToData_notToZero` 只用了 `1.2~2.4` 这种 >1 的值，恰好绕开了该分支。

### 2.4 做得好的（建议保持）

1. **`TideSpotRepository` 的降级链**：`CancellationException` 显式透传、未分类异常统一映射 `DataError.NetworkError`、gate 仅全部成功后记窗、`force` 绕 gate、首刷「数据时间」不回填 1970——FO-17 三修有代码有单测，工程质量高于平均水平。
2. **`hourly_score` v2→v3 与 vetoReasons 映射**：领域非空 `List` ↔ SQL 可空列的 `emptyList→NULL` 往返无损，`algoVersion` 入主键，CHG-08 ④ 落地干净。
3. **纯函数可测化**：`ChartMath` / `DaySelectorLogic` / `Derivations` 把逻辑从 Compose 中抽出，JVM 直接断言，符合 §7.2「算法可脱离手机验证」的思路。
4. **免责文案原文照用**（4 条逐字一致）、色带色值冻结、TalkBack `contentDescription` 覆盖主要交互控件。

## 3. 验收证据充分性说明（重要）

M4 退出标准写有「五维显示满 240 h」「TalkBack 可读」「空值断线」。本轮能证实的是**纯逻辑层**；以下结论目前**没有运行时证据**：

- 无 `:app` 模块 → `DetailScreen` 与 `MapScreen` 均无任何调用方，只能证明「可编译成 AAR」，不能证明「可显示」。
- `:core:ui` / `:feature:detail` 的 `build.gradle.kts` **没有 `ui-test-junit4` / `ui-test-manifest` / Robolectric**；§10.2 要求的「Compose UI：DaySelector 切 +9 出 24 行、FactorBreakdown 展开含权重、徽标文案」在 M4 无一条实现。M4 新增 35 个用例全是纯 Kotlin 逻辑测试。
- `unitTests.isReturnDefaultValues = true` 会静默吞掉 Android framework 调用，进一步削弱 JVM 测试的运行时代表性。

这解释了为什么 D01（Tab 标题数组）、D02（嵌套滚动）、D10（组件未接线）能在 377 全绿中漏网：**它们全在 Composable 组装层，而该层一行测试都没有**。建议把「补 Compose 冒烟测试」本身作为 M4 补验条件，而不是简单把缺陷改完就算过。

## 8. 结论

M4 的**底座是合格的**：数据层的降级、缓存、时区、评分落库与 377 个可复现单测，足以支撑后续里程碑，不必返工。问题集中在**「组件已实现，但接线、语义与一致性没走完最后一步」**——这正是纯 JVM 单测最擅长放过的一类缺陷。把 §4 的 P0/P1 闭环、把 Compose 冒烟测试补上，M4 就可以正式签署；而 §6 的 OPT-36（单一评分真源）、OPT-39（IANA 时区）、OPT-37（可信度面板）是 APP 完工后最值得先做的三件事，它们解决的是「用户看到的分数到底是不是系统算出来的那个分数」这一根本信任问题。
